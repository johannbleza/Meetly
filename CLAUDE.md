# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Meets is a macOS meeting assistant (SwiftUI + AppKit, Xcode project, Apple frameworks plus one SPM dependency: WhisperKit): live on-device transcription of mic + system audio, a floating always-on-top overlay with live captions and AI Q&A during a call, and post-meeting AI summaries/action items in the main window.

**Name:** the product is **Meets** (`PRODUCT_NAME`, every user-facing string, `Meets.app`). It was renamed from Meetly, and the internals keep that name on purpose: the bundle ID `johann.Meetly` (macOS permissions, `UserDefaults` and the login item are keyed to it), the `Application Support/Meetly` data folder (`AppStoragePaths`), the Swift module (`PRODUCT_MODULE_NAME = Meetly`), the Xcode project/target/folder names, type names like `MeetlyApp`, and log subsystems and debug notification names. Don't rename those without a migration. Brand sources (symbol, app icon SVGs) live in `design/brand/`; the app icon PNGs in `AppIcon.appiconset` are rendered from `meets-app-icon.svg` (sizes 16–64 use `meets-app-icon-small.svg`, which draws the symbol larger).

## Build

```sh
xcodebuild -project Meetly.xcodeproj -scheme Meetly build
```

Single target/scheme `Meetly`. No test targets exist. Deployment target is macOS 26.5 (uses the new `SpeechAnalyzer`/`SpeechTranscriber` and FoundationModels APIs). Usage-description strings live in `INFOPLIST_KEY_*` build settings, not a plist file.

**AI sign-in:** No API keys. Claude and Codex use the user's own subscription through the official `claude` and `codex` command-line tools, which must be installed and signed in. Settings live in `UserDefaults` via `Services/AppSettings.swift`.

## Architecture

`SessionManager` (`Services/SessionManager.swift`, `@MainActor @Observable`) is the hub: meeting state machine (idle/recording/paused/summarizing), overlay presentation state, chat messages, and all wiring between audio → transcription → SwiftData → AI. Starting a meeting hides the main window and shows the overlay; stopping reverses it.

**Main window:** No sidebar. `HomeShellView` owns a window toolbar (back/forward history over `home`/`meeting` routes, a centered search pill that opens search mode, the meeting control, and a settings button) and shows one full-width page: `MeetingsHomeView` (a band with the latest meeting, shown on both Meetings and Archived, then a Meetings/Archived filter over a list, grid or month calendar, `MeetingCalendarView`, with pinned meetings at the top of the Meetings list), search mode (`MeetingSearchView`, ⌘K: a large field backed by `SidebarSearchModel` over a keyboard-navigable list of `SearchResultRowView`s, each previewing the first transcript/summary match with it highlighted; the title-bar pill morphs into the field and back on springs, `SearchMorphDriver`, drawn under the toolbar by `SearchMorphLayer` while the toolbar background is hidden. The toolbar's principal slot only renders items containing a real control, so the pill wraps a placeholder `TextField`) or `SessionDetailView` (Summary / Transcript / Ask AI tabs, a floating Resume + ask bar). Settings is an in-window modal (`SettingsModal`), opened via `SessionManager.isSettingsPresented`. `AppTheme` colors are dynamic light/dark tokens; the main window follows `AppSettings.appTheme` (follows the system by default), while the overlay and notch panels always force dark.

**Main-window motion** (`Theme/AppMotion.swift`): page changes slide rather than crossfade. Opening a meeting or going forward pushes the new page in from the right over the old one, and going back reverses it (`HomeShellView.transitionPage`). Meetings ⇄ Archived keeps the featured meeting and the header in place and slides only the list sideways (Meetings on the left, Archived on the right; `MeetingsHomeView.filterSlide`), while the list title rolls in its own clipped line (`titleRoll`). Clickable views get the pointing-hand cursor through `clickableCursor()`. Detail tabs, list/grid/calendar and calendar months slide by direction. A removed view keeps its transition from its last update, so direction changes are applied one update before the change (`AppMotion.afterDirection`). The home list renders its first ~30 meetings eagerly (`MeetingsHomeView.eagerMeetingCount`): lazy rows created mid-animation land at their final spots instead of riding the featured meeting's curtain, which drew them over the meeting page on Back. The list layout lives in `@State`, not `@AppStorage`, because `@AppStorage` changes lost their animation. The list layout is one flat `ForEach` of headings and rows keyed by meeting (`MeetingsHomeView.listItems`), Pinned first, so pinning reorders a row and it moves instead of being copied (`matchedGeometryEffect` between the Pinned and day lists landed the row at its end spot at once). `PinStaging` plays a pin in beats, one at a time: a heading the meeting leaves empty rolls away (`AnyTransition.rollLine`: the line's height and its text animate together through a custom `Layout`), then the pin appears, then the row moves; unpinning reverses it. Headings follow the staged state and rows the saved `isPinned`.

**Audio pipeline:** `AudioCaptureService` (facade) owns `MicrophoneCapture` (AVAudioEngine tap) and `SystemAudioCapture` (ScreenCaptureKit, audio-only). Buffers flow through `AudioSourceRouter` into `LiveTranscriptionService`, which runs **two independent `TranscriptionChannel` instances** — one per source. "You" vs "Speaker" attribution is source-based (mic → `.me`, system audio → `.other`), not diarization.

**Transcription engines:** `TranscriptionEngine` in settings picks `WhisperChannel` (default; `Services/Whisper/`, on-device via WhisperKit) or `AppleSpeechChannel`. Whisper doesn't stream: `WhisperSegmenter` cuts audio into utterances by energy, re-decoding the growing utterance for live captions; `PartialTextStabilizer` only shows words two decodes agree on, so captions grow instead of rewriting. Both channels share one `WhisperRuntime`, which serializes decodes. Models are installed ahead of time from Settings (`WhisperModelStore`); if the selected model is missing or fails to load, the meeting falls back to Apple Speech with a warning rather than downloading or failing at start.

**AI:** `AIService` fronts three providers (`AIProvider`): Claude (default) and Codex, which launch the signed-in command-line tools (`Services/CLIAgents/`, model from settings), and on-device Apple Intelligence (`Services/FoundationModels/`). Apple Intelligence can't read images, so image questions route to whichever command-line tool is installed. Per-session controllers (`MeetingQAController`, `MeetingSummaryController`, `ActionItemsController`) each construct their own `AIService` and build prompts via `MeetingContextBuilder`.

**Persistence:** SwiftData only. `@Model` types in `Models/`: `MeetingSession` → cascade `TranscriptSegment` + `MeetingSummary` → cascade `ActionItem`, and cascade `QAMessage` (Ask AI history: overlay questions during the call and detail-page questions, saved as question/answer pairs on success; errors aren't saved). Final transcript segments are saved immediately as they arrive.

**Overlay:** `Overlay/OverlayPanelController` hosts a borderless floating `NSPanel` (all Spaces, forced dark, ⌘V image paste). Global hot key ⌘\ toggles it (Carbon, `OverlayKeyboardShortcutController`). `ScreenShareExclusion` sets `sharingType = .none` on all windows so Meetly is invisible in screen shares (toggleable in settings).

**Notch overlay:** Meetings always start with the overlay docked in the notch (`Overlay/Notch/`). `NotchPanelController` hosts a second borderless panel above the menu bar (`.mainMenu + 3`, all Spaces, fullscreen auxiliary). Its fixed canvas is centered on the hardware notch, or on a black "virtual notch" on screens without one (`NotchGeometry`). `NotchOverlayView` derives what it shows (compact ears, captions, hover controls, idle/call prompt, AI answer, countdown row) from `SessionManager` and morphs `NotchShape` with the springs in `Overlay/Motion/OverlayPhysics`. Dragging the bottom pill of the open notch, or of an AI answer (which stays on top, with the transcript under it), only resizes it (scrollable transcript history); dragging anywhere else on it stretches the notch a little, and then (past ~28 pt) the notch gives way and the floating overlay is pulled out of it by the drag (`Overlay/Motion/NotchTearOff`): how far it's out follows the pull, pushing back up takes it back in, past ~140 pt or on a downward flick it pours the rest of the way out on its own under the pointer, and letting go early swallows it back into the notch. The real panel stays parked where it was ordered in and the mesh draws it at the pointer; once it's all the way out it's moved there and unwarped, so the handoff to a plain floating drag doesn't jump. Dragging the floating toolbar up to any display's notch (the MacBook's real one, or another screen's virtual one) docks it there, and it stays on that screen while shown. Whenever the overlay opens from hidden (⌘\, a recording starting, a detected call), it opens on the display under the pointer (`NotchMetrics.activeScreen`, `OverlayPanelController.moveToActiveScreen`); ⌘\ while it's open on another display brings it over instead of hiding it. `OverlayPanelController` is the facade over both panels and routes by `SessionManager.overlayDock`. Detaching and docking use the same genie as the main window (below), on the floating panel itself (`OverlayPanelController.overlayGenie`): a tear-off or pop-out closes the notch into one reaching for the funnel (`beginPouringOut`) and pours the panel out of its mouth; docking sucks the panel up into the mouth while the notch reaches for it and gulps open (`absorb`). The panel's window is a taller transparent canvas, so the genie funnels only the drawn panel (`OverlayMotion.panelHeight`, measured by `OverlayView`) and folds the empty rest flat. Reduce Motion or a refused warp just shows or hides the panel. `WindowSpringAnimator` moves the floating window on a display link (flings and settling). DEBUG builds have a demo driver for tuning without audio, the store or the AI tools: launch a Debug build (`-configuration Debug`; the default build is Release) with `-MeetlyNotchDemo YES` (add `-hideFromScreenShare NO` to screenshot it) and post the distributed notification `johann.Meetly.debug.notch` with a step name as its object (`recording`, `speak`, `ask`, `answer`, `countdown`, `popOut`, `dock`, `picker`, …; see `SessionManager.debugApplyNotchDemo`). The `tearOff`, `tearHold`, `tearFlick`, `tearCancel` and `tearBack` steps script a pull out of the notch (`NotchPanelController.debugScriptedPull`), which skips the SwiftUI gesture; `-MeetlyGenieTrace YES` also logs the tear-off's frames (`TearOffTrace`).

**Main window ⇄ notch genie:** Starting a meeting sucks the main window into the notch like minimize sucks a window into the Dock, and stopping pours it back out (`OverlayPanelController.showAbsorbingMainWindow` / `hideIntoMainWindow`). Stopping from the floating overlay first sucks the overlay into the notch (slower than a dock, still drawn as the meeting panel: `OverlayMotion.holdsMeetingLayout`), and the window starts pouring out once about two thirds of it is in (`stopHandoff`; on another display it waits until the overlay is all the way in), launched out of the mouth (`expand(launched:)`) so it doesn't ease out of hiding as a visible pause. `WindowGenieController` (`Overlay/Motion/WindowGenie.swift`) warps the real window, live pixels and all, with the WindowServer's private `CGSSetWindowWarp` (looked up with `dlsym`; the mesh is 32-bit floats, window points → global top-left points). Snapshots can't stand in: `cacheDisplay` and `CALayer.render` come back blank for SwiftUI content on macOS 26, and ScreenCaptureKit needs TCC and skips `sharingType = .none` windows. The mesh is `GenieMesh`, a pure function of one progress value, so it can be rendered offline: the sides bend into an S-funnel down from a mouth just inside the notch (`NotchPanelController.genieTarget()`), then the content slides up through it, top rows first. Progress runs on two cascaded critically damped `LiquidSpring`s (`WindowGenieController`, one instance per window), so it eases in and out and turns around mid-flight with its momentum (start during a stop, or stop during a start). While it runs, the window ignores the mouse, has no order-in/out animation, and sits at `.mainMenu + 2`, over the menu bar and under the notch, which hides the mouth. The notch reaches for the funnel (`setReach`) and gulps open (`absorb`) when most of it is in; on stop it shrinks to a reaching notch (`beginPouringOut`) and lets go as the window comes out. A finished collapse leaves the window at alpha 0 for a second before ordering it out (`finishHiding`), because ordering the key window out stalls the main thread mid-gulp. It falls back to the instant hide/show with Reduce Motion, a full-screen, minimized or covered window, a window on another display from the notch, or a refused warp. DEBUG: demo steps `mainWindow`, `windowToNotch`, `notchToWindow`; `-MeetlyGenieTrace YES` logs frame pacing and why it fell back; `-MeetlyGenieSlow YES` runs it ten times slower.

**Screenshots:** "Ask about screen" in the overlay takes one full-size frame from the meeting-audio `SCStream` (temporarily raising its 2×2 resolution) and sends it to `askQuestion`. Don't use `SCScreenshotManager`: the picker's approval only covers the stream, so screenshots fail Screen Recording TCC. It opens the share picker if meeting audio isn't on. The panel goes to alpha 0 during capture because recent macOS versions don't reliably honor `sharingType = .none` for ScreenCaptureKit.

**Meeting detection:** `Services/MeetingDetection/` needs no calendar. `AudioProcessMonitor` polls Core Audio's per-process objects for which apps hold the mic, excluding Meetly's own PID. `MeetingDetector` treats the known call apps in `MeetingApp.all` (Teams, Zoom, Webex, Slack, FaceTime, …) as calls; for browsers (`MeetingBrowser`: Chrome, Safari, Edge, Brave, Arc, …) it asks `BrowserMeetingProbe` to match open tab URLs against known meeting sites (Automation permission). Any other app holding the mic, or a browser with no matching tab, still gets a generic "X is using your microphone" prompt (`OtherMicApp`, which skips system services and recording/dictation apps). Confirmed calls win over generic ones. `SessionManager.reconcileDetection()` turns that into the start prompt in the idle overlay and the auto-stop countdown. It's idempotent and runs after every poll.

## Critical constraints (violating these reintroduces fixed bugs)

- **PCM buffers never touch the MainActor.** The capture-thread → router → speech-channel path uses `nonisolated(unsafe)` callbacks and lock-guarded `@unchecked Sendable` types (`AppleSpeechChannel`, `LiveTranscriptionService.ChannelStorage`). Don't add MainActor hops to the audio path.
- **The overlay panel window is a fixed-size transparent canvas** — fold/expand is a pure SwiftUI animation inside it; `updateForPresentation` deliberately never resizes the `NSPanel`. Resizing the window reintroduces clipping/jitter. The same goes for the notch panel: its states are SwiftUI shape changes inside a fixed canvas, and the tear-off/dock genie only warps and moves windows.
- **Clicks pass through the notch canvas because of a pointer poll**, not alpha: `NotchPanelController.pointerTick` toggles `ignoresMouseEvents` against the live shape frame, which keeps menu-bar items and windows under the transparent canvas clickable. Keep each notch state's content height stable (the fixed caption box) so live captions don't make the notch wobble.
- **Every exit from the genie puts the main window back.** `WindowGenieController.finish()` (reached by settling, `cancel()` and a watchdog) and `finishHiding()` clear the warp and restore the level, mouse, animation behavior and alpha; `showMainWindow()` / `hideMainWindow()` cancel a running genie, and `showMainWindow()` clears any warp. `NotchTearOff` does the same for the overlay: it ends only through `handOff()` (out, moved to where it's drawn, then unwarped) or `putBack()` (ordered out, then unwarped), reached by settling, `cancel()` (every `OverlayPanelController` entry point calls `endTearOff()` first), a refused warp and a watchdog. A window left warped is invisible or bent, so don't add a path that skips them. The warp is private API: anything that calls it must fall back to the plain hide/show when it's refused. Don't resize the real window for it either.
- **A window without a shadow isn't drawn while it's poured out of a warp** unless `WindowWarp.PourOutKick` turns the shadow on for its first frames that show some of it (it's still under the notch then). Without it the floating overlay's pour-out (pop-out, tear-off) plays invisibly and the panel just appears at the end; if the kick ends while every row is still piled into the mouth, it's invisible again. The main window has a shadow, so it never needed this. Any new pour-out of the overlay needs the kick.
- **Window animations are paced by a screen's display link, not the window's** (`NSScreen.displayLink`: the mouth's display for the genie, the destination display for `WindowSpringAnimator`). A window dragged or flung mostly off its display stops getting its own frames, which froze the genie until its watchdog cut to the end and stranded the panel off screen.
- **The notch pull is a SwiftUI `DragGesture`**, not an AppKit tracking view: AppKit views behind SwiftUI `Text` never receive mouseDown. The floating overlay's drag region moves the window itself instead of `performDrag`, which can't reach the menu bar where the notch is.
- **In notch dock, the notch panel is the share picker's key window** when the main window is hidden (`OverlayPanelController.presentKeyWindowForPicker`).
- **System audio capture must go through `SCContentSharingPicker`**, never `SCShareableContent` — programmatic capture re-triggers the Screen Recording TCC dialog even when granted. The picker must be presented *before* hiding the main window (it needs a key window or it silently cancels); see `SessionManager.prepareForContentSharingPicker()`.
- **SwiftData migrations are destructive**: `MeetlyApp` deletes and recreates the store if migration fails. Add new model fields as optionals with a defaulting accessor (see `MeetingSession.isArchived`/`isArchivedValue`) to avoid wiping user data.
- The system speech channel is eager-started before any system audio arrives to avoid a cold-start transcription gap; `feedSystemBuffer` lazily restarts it if missing.
- Mic transcripts matching recent meeting audio are dropped as speaker bleed (`MicBleedFilter`, applied in `SessionManager`). This compares transcripts on purpose: earlier buffer-level gates (`MicEchoGate`, RMS thresholds) also cut the user's own speech.
- Consecutive final transcripts from the same speaker within 3s are merged into one bubble (`SessionManager.shouldMergeTranscript`).
- **Detected calls prompt instead of starting a recording**, because system audio needs a click on the share picker. Auto-stop always shows a cancellable countdown because mic release is only an inferred end of call, and it only applies to recordings that overlapped a detected call. It must not fire during `startMeeting()`: `stopMeeting()` removes the picker observer, which would leave the picker continuation unresumed.
- **Meetings with no transcript are deleted when they stop** (`SessionManager.stopMeeting`), so the session row created at start never shows up as an empty meeting.
- **Continuing a meeting** (`SessionManager.continueMeeting`, "Continue Meeting" in the detail header) records into the existing session. The time between recordings goes in `MeetingSession.continuationGapDuration` and is left out of `duration`. Stopping with no new segments puts `endedAt` and the gap back as they were and keeps the old summary; otherwise the summary is replaced, not duplicated.
- **Silent recordings stop themselves** (`SessionManager.reconcileIdleStop`, `AppSettings.idleRecordingStopMinutes`), which covers recordings with no detected call. Transcripts and user actions restart the timer. It skips paused recordings and detected calls, because a call can be quiet for long stretches, and it also must not fire while the share picker is open.
- **App sandbox is off** because a sandboxed app's child processes inherit the sandbox and can't reach the CLI tools' sign-ins. Keep the audio-input entitlement in `Meetly/Meetly.entitlements`. `LegacyContainerMigration` copies data out of the old container on first launch.
- **Store data under `AppStoragePaths`**, never at SwiftData's or Application Support's default location. Unsandboxed, those are shared with other apps, and `MeetlyApp` deletes the store when migration fails.
- **Transcripts are untrusted input to the CLI tools**: anyone on a call can speak instructions into them. `CLIAgent` must keep shell and file tools off, ignore user settings, MCP servers and hooks, run in an empty temp directory, and not save session history. Web search is the only tool allowed. It also strips API-key variables from the environment so usage stays on the subscription.
